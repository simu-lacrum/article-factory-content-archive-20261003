## Evidence a responsible listing should show

The product page should include a dated compatibility status, supported Windows versions, local-only visibility disclosure, representative images, removal instructions and a real support route. A cosmetic count should explain whether variants and individual slots are counted separately.

Release notes should identify changes caused by a Dota update. If every entry says only “fixed” or “updated,” the buyer cannot tell whether the developer retested the asset loader, interface, cosmetic database or all three.

Preserved media is useful for judging interface and coverage, but pair it with the current status. An older screenshot is historical evidence, not a live compatibility certificate.

Support documentation should also state what happens to saved presets when a cosmetic disappears or an identifier changes. Silent substitution can produce the wrong model or effect. A maintained database removes invalid entries, communicates migrations and lets the user return to the default item without manual file surgery.

If the tool includes automatic updates, verify the update origin and whether the package is signed. An updater has ongoing permission to replace code, so its trust requirements are higher than those of a static image archive.

Disable abandoned updaters and remove their scheduled tasks; an inactive cosmetic interface can still leave an active background component.
