## Visual and information modules

Visual modules may draw ranges, cooldowns, inventory panels, ward reminders or entity markers. First ask whether the source is already visible to the player. A timer based on a visible event is different from a feature claiming to reveal data hidden by fog of war. The latter has a more direct enforcement precedent and should never be described as a harmless overlay.

For every indicator, check its trigger, duration, scope and fallback. Does it cover every hero or only a documented set? Does it show an estimate as an estimate? Can it be disabled without closing the rest of the client? Those details are more useful than “full vision” or “advanced ESP” as a headline. Our [Dota 2 maphack claims guide](https://dota2cheat.com/guides/dota-2-maphack-guide) explains why hidden-information wording deserves extra scrutiny.

## Targeting and cast assistance

Targeting aids can sort nearby units, suggest a cast position, or choose a configured priority. Prediction may account for movement and projectile travel. Latency, immunity, dispels, reflection and vision still affect the result. A valid target is not always the correct target, so automation cannot replace the player’s decision.

Ask whether a module sends an input or only displays a suggestion. Ask what happens when two targets meet the same condition, and what stops the sequence if the ability is on cooldown. A short answer that names edge cases is stronger evidence than a longer feature list.

## Hero scripts and combo logic

Hero scripts connect conditions to abilities, items and target priorities. The useful specification is not “one-click combo”; it is the list of supported heroes, order rules, stop conditions and configuration options. Patch changes can invalidate item names, talent assumptions, cast ranges and the timing used by a sequence.

Enable one module at a time and record the hero, mode and build you tested. If a provider cannot say what happens on an unsupported hero, assume the profile is not portable. Read the [Dota 2 scripts terminology guide](https://dota2cheat.com/guides/dota-2-scripts-guide) for the difference between a bind, a macro, a rule and full automation.

## Farming and utility tools

Last-hit indicators, stack timers, rune reminders, camera controls and inventory panels may reduce repeated interface work. Their usefulness depends on role: a support may care about ward and enemy-item context, while a carry may value farming cues. Count observable jobs, not toggles. Five settings that change one panel are not five independent systems.

## Cosmetics and interface changes

Cosmetic labels can refer to local visual changes, custom models or a skin changer. The label does not establish whether the change is visible only to the user, supported after updates, or permitted by the game’s rules. Treat a screenshot as evidence of appearance at one moment, not evidence of current operation or current support.

## Turn marketing into a test sheet

1.   Write the feature name exactly as listed.
2.   Describe the visible output or input it promises.
3.   Record the data source, hero/mode scope and stop condition.
4.   Check the current build date and the provider’s update channel.
5.   Mark unknown claims as unknown instead of filling the gap with a forum post.

For example, rewrite “smart target selection” as: which units are eligible, how are priorities ordered, and when does the module stop? Rewrite “ward tracker” as: which event creates a marker, how long does it remain, and is it an observation or an estimate? Rewrite “auto combo” as: which order is used, what happens during immunity, and how can the player cancel it?

This translation also exposes duplicated marketing. A panel may have separate toggles for range, cooldown and status while all three use one visual data source. Count user-visible jobs and documented boundaries, not the number of switches. Record the result with the date and client build because a screenshot can remain online long after an item, hero or interface event changes.
